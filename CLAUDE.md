# Layers — правила для Claude и других ИИ-ассистентов

Как устроена команда и что уже решено — в `docs/HANDBOOK.md`, этот файл его
не заменяет. Здесь только то, что ассистенту надо знать, чтобы работать так
же, как команда.

## Где правда

| Что | Где |
|---|---|
| Как работаем, сроки, **принятые решения** (раздел 8) | `docs/HANDBOOK.md` |
| Эндпоинты, форматы, коды ошибок | `docs/API.md` |
| Атрибуты одежды и их значения | `docs/attributes.md` |
| Таблицы и поля | `docs/db-schema.md` |
| Как бэк вызывает движок подбора | `docs/engine.md` |

Не дублируй содержимое этих файлов сюда или в код-комментарии. Приняли
решение — допиши его в раздел 8 HANDBOOK с датой, коротко и со ссылкой на
файл с подробностями.

## Порядок работы

- **Сначала документ, потом код.** Новое поле, эндпоинт, ошибка или колонка —
  сначала PR в `docs/`, после его мержа — код. По разделам API.md со статусом
  «черновик» код не пишем.
- **Одна ветка — одна задача**, от свежего `main`: `feat/...`, `fix/...`,
  `docs/...`.
- **Коммиты и PR — по-русски**, заголовок «Область: что сделано», описание PR
  по шаблону из HANDBOOK (Что сделано / Как проверить / На что посмотреть
  ревьюеру / Связано с).
- **Никакой атрибуции ИИ** — ни `Co-Authored-By`, ни «Generated with …», ни
  ссылок на сессии: ни в коммитах, ни в описаниях PR, ни в комментариях.
- **Мерж.** В сессиях Ники (GitHub `zeawale`) Claude мержит свои PR сам —
  `gh pr merge N --merge --admin --delete-branch`, docs-PR раньше кода, и
  только после проверки на живом стеке. Чужие PR не мержит. Если по HANDBOOK
  нужно согласие ещё кого-то, ждёт его. У остальных участников — как в
  HANDBOOK: PR на ревью Нике.

## Проверка

- Стек: `docker compose up -d`. Бэк сам применяет миграции и перезагружается
  при правке кода. Если оболочка не видит `docker`, он в `~/.docker/bin`.
- Проверяем на живом стеке скриптом внутри контейнера:
  `docker compose exec -T backend python - < check.py` — через
  `fastapi.testclient.TestClient` или `httpx` на `localhost:8000`.
- Тестовые данные удаляем за собой. Тестовые email — `@example.com`
  (`.test` валидатор не пропускает).
- Настоящих писем не шлём: на время проверки подменяем `app.services.mail.send`.
- Миграции: `alembic revision --autogenerate`, потом привести к стилю 0001
  (заголовок по-русски, без автокомментариев alembic), затем `alembic check`
  и откат с повторным накатом.

## Что полезно знать

- Где бэк уже готов — отметки «Бэк готов (#N)» в `docs/API.md`.
- Движок подбора — `backend/app/engine/`. Сейчас там заглушка `stub.py`; Настя
  заменяет её, не трогая сигнатуру из `docs/engine.md`.
- Модели распознавания лежат в образе в `/opt/models`, их качает
  `backend/scripts/download_models.py` при сборке. Первое распознавание после
  старта бэка — около 20 с, процесс с моделями занимает около 2 ГБ памяти.
- Загрузчик Hugging Face внутри Docker на этой машине зависал — модели качаем
  по прямым ссылкам, а не через `huggingface_hub`.

## Нельзя

- Читать и править `.env`, вписывать пароли, ключи и токены — это делает
  человек. Новая переменная — в `.env.example` с пустой заглушкой.
- Коммитить `frontend/package-lock.json` — это решает Саша.

## Бэкенд коротко

Полные правила — HANDBOOK, раздел 7.

- Эндпоинты, которые ходят в базу, — `def`, не `async def` (`app/database.py`).
- Запросы к базе не в цикле: связанные данные — `selectinload`/`lazy="selectin"`.
- Ошибки — `{"detail": "..."}` по-русски, чтобы показать как есть. Чужое —
  `403`, нет — `404`, кроме мест, где API.md говорит «не различаем».
- Списки атрибутов — только из `app/services/attributes.py`.

## Фронтенд

Общие правила — HANDBOOK, раздел 7. Здесь — как раскладываем код внутри
`frontend/src/`, чтобы экраны не превращались в один файл на 400 строк.

### Папки

| Папка | Что там | Пример |
|---|---|---|
| `api/` | Все запросы к бэку. `client.js` — адрес, токен, разбор ошибок. Остальное — по файлу на раздел API.md, в каждом функции-обёртки | `auth.js`: `login(email, password)`, `register(...)` |
| `pages/` | Один файл — один экран. Держит состояние экрана, вызывает `api/` и собирает экран из компонентов | `Login.jsx`, `Onboarding.jsx` |
| `pages/<экран>/` | Части большого экрана, которые больше нигде не нужны | `pages/onboarding/CityStep.jsx` |
| `components/` | Куски интерфейса, которые нужны на двух и больше экранах. Один компонент — один файл | `FormField.jsx`, `BackButton.jsx`, `ColorPicker.jsx` |
| `hooks/` | Общая логика без разметки | `useAttributes()`, `useAuth()` |
| `theme.js` | Все цвета, шрифты, размеры и вид MUI-компонентов | |

### Компоненты

- Экран длиннее ~150 строк — выносим шаги и блоки в отдельные файлы.
- Одинаковый JSX в двух местах — один компонент с пропсами. Пример: блоки
  «Люблю носить» и «Не ношу» в онбординге — это один `ColorPicker`
  с `selected`, `disabled` и `onToggle`.
- Компонент получает данные пропсами и сам в бэк не ходит. Запросы — на
  странице или в хуке.
- Повторяющиеся кусочки (кнопка «Назад», подпись над полем + поле) — сразу
  в `components/`, а не копией в каждый экран.

### Стили

- Цвета только из темы: `primary.main`, `text.secondary`, `divider`. Хекс
  (`'#1c1b18'`) в компоненте — ошибка. Нужен новый цвет — сначала в
  `theme.js`, потом использовать по имени.
- Текст — через варианты темы (`variant="body2"`, `"h3"`), а не
  `fontSize: 15, fontWeight: 600` в каждом месте. Нет подходящего варианта —
  добавить его в `typography` темы.
- Вид MUI-компонентов, который повторяется (поля, кнопки, карточки), задаём
  один раз в `theme.components.<Имя>.styleOverrides`. Никаких `fieldSx`,
  скопированных в несколько файлов.
- `sx` — только для разовой раскладки: отступы, `display`, `gap`, ширина.
- Цвета кружков справочника цветов (`black`, `navy`…) — одним объектом в
  `theme.js`, а не в странице.
- Размеры, отступы, цвета и шрифты берём из Figma (Dev Mode или Figma MCP),
  а не на глаз. Ширина экрана — 390 px.

### Данные и запросы

- Списки атрибутов — только из `GET /attributes`: один раз на приложение
  (хук или контекст), ни значений, ни подписей в коде.
- Ошибки: `detail` — строка, у `422` — список ошибок по полям, его
  разбираем и показываем под полями.
- Токен — только через `api/client.js`. Экраны приложения без токена ведут
  на `/login`. При запуске — `GET /users/me`: онбординг не пройден → `/onboarding`.
- У каждого запроса есть состояние загрузки (спиннер или скелетон) и
  состояние ошибки (текст и «Повторить»). Молча глотать ошибку нельзя.

### Проверка перед PR

- `npm run build` — без ошибок.
- Пройти руками всё из «Как проверить» в описании PR на ширине 390 px.
- В PR только файлы из `frontend/` (бэк и `docs/` — отдельными PR).
