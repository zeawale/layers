# API.md

Источник правды по эндпоинтам. Фронт и бэк договариваются здесь **до** того,
как что-то написано в коде. Если нужного эндпоинта в этом файле нет —
сначала описываем и согласуем, потом пишем.

Порядок изменений: отдельная ветка → PR с правкой `API.md` → согласование →
только после этого код.

Статусы разделов:

- **Согласовано** — по этому можно писать код.
- **Черновик** — общий вид понятен, детали поменяются. Код по черновику не пишем.

## Соглашения

- Базовый адрес в разработке: `http://localhost:8000`
- Формат: JSON, кодировка UTF-8. Исключение — загрузка фото, там `multipart/form-data`.
- Аутентификация: заголовок `Authorization: Bearer <token>`. Токен нужен
  везде, кроме `/health*` и `/auth/*`. Дальше по тексту это не повторяется.
- Даты и время: ISO 8601, UTC (`2026-09-28T10:00:00Z`). Даты без времени — `2026-09-28`.
- Ошибки: тело `{"detail": "текст ошибки"}`. Текст — по-русски, его можно
  показывать пользователю как есть.
- Значения атрибутов одежды берутся из `docs/attributes.md`: `category`, `color`,
  `style` — строки с машинными именами, `warmth` — число 1–5, `season` — список
  строк (у вещи может быть несколько сезонов), `water_resistance` — `true`/`false`.
  Списки допустимых значений фронт **не хардкодит**, а берёт из `GET /attributes`.
- Все объекты, у которых есть владелец, отдаются только владельцу. Запрос
  чужой вещи или комплекта — `403`.
- Пагинации нет: гардероб одного человека — десятки вещей, не тысячи.
  Если понадобится — добавим `limit`/`offset` отдельным PR.

### Коды ответов

| Код | Когда |
|---|---|
| 200 | Успех |
| 201 | Создан объект |
| 204 | Успех, тела нет (удаление) |
| 400 | Кривой запрос: логически неверный, хотя по форме валидный |
| 401 | Нет токена или он протух |
| 403 | Токен есть, но объект чужой |
| 404 | Объекта нет |
| 409 | Конфликт: email уже занят, другого варианта комплекта нет, комплект на сегодня уже отмечен как надетый |
| 413 | Файл слишком большой |
| 415 | Неподдерживаемый тип файла |
| 422 | Не прошла валидация тела запроса (FastAPI отдаёт сам, формат `detail` у него свой — список ошибок по полям) |
| 429 | Лимит исчерпан: вариантов комплекта на сегодня больше нет |
| 502 | Внешний сервис не ответил: Open-Meteo (прогноз, поиск городов) или Nominatim (город по координатам) |

## Общие объекты

Объекты, которые встречаются в нескольких ответах. Описаны один раз здесь,
дальше на них ссылки.

### User

```json
{
  "id": 1,
  "email": "nika@example.com",
  "name": "Ника",
  "city": "Санкт-Петербург",
  "lat": 59.94,
  "lon": 30.31,
  "preferences": {
    "style": "casual",
    "liked_colors": ["black", "gray"],
    "disliked_colors": ["yellow"]
  },
  "avatar": { "id": 20, "url": "/media/photos/Hn4pZ0aWm-Q7uE1xKcJr5w.jpg" },
  "onboarding_completed": true,
  "created_at": "2026-09-28T10:00:00Z"
}
```

- `avatar` — фото профиля, объект Photo. `null`, если не загружено — тогда
  фронт показывает первую букву имени (или email, если имени нет).
- `name` — как обращаться в интерфейсе («Доброе утро, Ника»). Необязательное,
  до 50 символов, пробелы по краям бэк обрезает. `null`, если не указано, —
  тогда фронт пишет приветствие без имени.
- `city`, `lat`, `lon` — `null`, пока пользователь не указал город. Координаты
  хранятся с точностью до двух знаков (~1 км): для прогноза этого достаточно,
  а точный адрес человека нам хранить незачем.
- `preferences.style` — значение из справочника `style`; `null`, если не выбран.
- `liked_colors`, `disliked_colors` — значения из справочника `color`, могут быть
  пустыми. Один цвет не может быть в обоих списках сразу.
- `onboarding_completed` — `true`, когда указан город. Стиль и цвета можно
  пропустить: без стиля движок подбирает вещи любого стиля. Фронт по этому
  флагу решает, показывать онбординг или главный экран.

### Photo

```json
{
  "id": 17,
  "url": "/media/photos/2c7Vq_Lx9TbN3kRwYe8sAg.jpg"
}
```

`url` относительный, фронт подставляет базовый адрес бэкенда. Файл отдаётся
как статика, без токена. Поэтому имя файла случайное, а не `id`: по номерам
нельзя перебрать чужие фото. Фронт `url` не разбирает и не собирает сам —
берёт из ответа как есть.

### Item

Вещь гардероба.

```json
{
  "id": 42,
  "name": "Серый свитер",
  "category": "top",
  "color": "gray",
  "warmth": 3,
  "style": "casual",
  "season": ["demi", "winter"],
  "water_resistance": false,
  "photo": { "id": 17, "url": "/media/photos/2c7Vq_Lx9TbN3kRwYe8sAg.jpg" },
  "created_at": "2026-10-15T12:00:00Z",
  "updated_at": "2026-10-15T12:00:00Z"
}
```

- `name` — как вещь называется в интерфейсе и в тексте объяснения. Обязательно, до 100 символов.
- `category`, `color`, `warmth` — обязательны, без них движок вещь не видит.
- `style`, `season`, `water_resistance` — необязательны. Отсутствие трактуется
  по справочнику: без `style` вещь подходит под любой стиль, пустой `season` —
  всесезонная, `water_resistance` по умолчанию `false`. В ответе поля есть всегда:
  `style: null`, `season: []`, `water_resistance: false`.
- `warmth` — число 1–5 по шкале из справочника.
- `photo` — `null`, если фото нет.

### Weather

Погода на день, по которой собран комплект.

```json
{
  "date": "2026-11-09",
  "city": "Санкт-Петербург",
  "temp_min": 2.1,
  "temp_max": 6.8,
  "feels_like": 1.5,
  "wind_speed": 7.2,
  "precipitation": 3.4,
  "precipitation_probability": 80,
  "condition": "rain"
}
```

- Температуры в °C, ветер в м/с, осадки в мм за день.
- `precipitation_probability` — вероятность осадков за день, целое 0–100 (%).
  Берём дневной максимум `precipitation_probability_max` из Open-Meteo. `null`,
  если Open-Meteo его не отдал. Фронт показывает проценты, движку полезнее
  `precipitation` в мм — поэтому оба поля.
- `feels_like` — минимальная «ощущается как» за светлое время суток: одеваемся под худший момент дня, а не под средний.
- `condition` — одно из `clear`, `cloudy`, `rain`, `snow`. Сводим из кодов Open-Meteo на бэке, фронту с их кодами не возиться.

### Outfit

Комплект на день.

```json
{
  "id": 7,
  "date": "2026-11-09",
  "variant": 1,
  "selected": true,
  "weather": { "...": "объект Weather" },
  "items": [ { "...": "объект Item" } ],
  "explanation": "На улице +2 и дождь. Свитер и непромокаемая куртка — чтобы не замёрзнуть и не промокнуть; тёмные джинсы — под стиль casual.",
  "missing": [],
  "feedback": null,
  "created_at": "2026-11-09T06:00:00Z"
}
```

- `variant` — номер варианта за этот день, с 1. Растёт на единицу с каждым
  «другим вариантом» и не переиспользуется.
- `selected` — этот вариант сейчас выбран как комплект дня. На один день у
  пользователя выбран ровно один вариант.
- `items` — вещи из гардероба пользователя, по одной на категорию: верх (или
  платье), низ, при необходимости верхняя одежда и обувь. Подслоёв нет — см.
  `category` в справочнике. Удалённая из гардероба вещь из комплекта
  пропадает (см. `DELETE /items/{id}`), поэтому у старого комплекта `items`
  может оказаться короче, чем был, или пустым.
- `explanation` — текст от движка. Обязательное поле, не пустое.
- `missing` — категории, которых не хватило в гардеробе для этой погоды
  (например, `["outerwear"]`). Пустой список — всё нашлось. На этапе 5 сюда
  же привяжутся партнёрские товары.
- `feedback` — `null`, пока пользователь не оценил; после оценки — объект из раздела «Оценки».

### OutfitDay

Все варианты комплекта на один день. Главный экран работает с этим объектом:
показывает выбранный вариант, переключается между остальными без новых
запросов и знает, можно ли попросить ещё один.

```json
{
  "date": "2026-11-09",
  "variants": [
    { "...": "объект Outfit, variant 1, selected: false" },
    { "...": "объект Outfit, variant 2, selected: true" }
  ],
  "selected_id": 8,
  "variants_max": 3
}
```

- `variants` — варианты по возрастанию `variant`. Всегда хотя бы один.
- `selected_id` — `id` выбранного варианта, чтобы фронту не искать `selected: true`.
- `variants_max` — сколько вариантов можно получить за день. Число задаётся в
  настройках бэка (по умолчанию 3), фронт его не хардкодит. Кнопка «Другой
  вариант» активна, пока `variants.length < variants_max`.
- Подпись «Вариант 2 из 3» — это `variant` выбранного и `variants_max`.

## Авторизация

Статус: **согласовано**. Нужно к 12 октября.

Схема простая: один JWT-токен на 7 дней, без refresh. Когда протух — фронт
получает `401` на любой запрос, чистит токен и отправляет на экран входа.
Токен хранится в `localStorage`.

После смены пароля (через сброс или из профиля) все токены, выданные
раньше, перестают работать: если кто-то чужой был залогинен с этим аккаунтом, его выкинет.
Для фронта это тот же `401`.

### `POST /auth/register`

Регистрация. Авторизация не нужна. Сразу возвращает токен — отдельно логиниться после регистрации не надо.

Тело запроса:

```json
{
  "email": "nika@example.com",
  "password": "не-менее-8-символов",
  "name": "Ника"
}
```

`name` — необязательное, до 50 символов. Пустая строка — то же, что не передать.

Ответ `201`:

```json
{
  "access_token": "eyJhbGciOi...",
  "token_type": "bearer",
  "user": { "...": "объект User" }
}
```

Ошибки:

- `409` — email уже зарегистрирован.
- `422` — email невалидный, пароль короче 8 символов или имя длиннее 50.

### `POST /auth/login`

Вход. Авторизация не нужна.

Тело запроса:

```json
{
  "email": "nika@example.com",
  "password": "..."
}
```

Ответ `200`: такой же, как у регистрации (`access_token`, `token_type`, `user`).

Ошибки:

- `401` — неверная пара email/пароль. Один и тот же текст в обоих случаях,
  чтобы по ответу нельзя было понять, существует ли email.

### `POST /auth/password-reset/request`

«Забыли пароль?»: отправить на почту ссылку для сброса. Авторизация не нужна.
Код — после 9 ноября: к 12 октября хватает регистрации и входа.

Тело запроса:

```json
{ "email": "nika@example.com" }
```

Ответ `204`, без тела — **всегда**, есть такой email или нет. Иначе по ответу
можно было бы перебором узнать, кто у нас зарегистрирован. Фронт показывает
один и тот же текст: «Если аккаунт с этим адресом есть, мы отправили ссылку».

Как это работает:

- В письме ссылка `<адрес фронта>/reset-password?token=<токен>`. Адрес фронта
  бэк берёт из настроек.
- Токен одноразовый и живёт 60 минут. Новый запрос отменяет все прошлые
  токены этого пользователя.
- Чаще раза в минуту на один адрес письмо не уходит, но ответ всё равно `204`.

Ошибки: `422` — email невалидный.

### `POST /auth/password-reset/confirm`

Задать новый пароль по токену из письма. Авторизация не нужна.

Тело запроса:

```json
{
  "token": "из-ссылки-в-письме",
  "password": "не-менее-8-символов"
}
```

Ответ `200`: такой же, как у входа (`access_token`, `token_type`, `user`) —
человек сразу залогинен, второй раз вводить пароль не нужно.

Ошибки:

- `400` — токена нет, он истёк или уже использован. Эти случаи специально не
  различаем. `detail`: «Ссылка больше не работает, запроси новую».
- `422` — пароль короче 8 символов.

### `POST /auth/password/change`

Сменить пароль из профиля (экран «Пароль» в 4.2). Авторизация нужна.

Тело запроса:

```json
{
  "current_password": "...",
  "new_password": "не-менее-8-символов"
}
```

Ответ `200`: такой же, как у входа (`access_token`, `token_type`, `user`).
Фронт заменяет токен в `localStorage` на новый: все старые токены после
смены перестают работать, как и при сбросе, а этот выдан уже после смены.

Ошибки:

- `400` — текущий пароль неверный. `detail`: «Неверный текущий пароль».
  Именно `400`, не `401`: на `401` фронт чистит токен и выкидывает на вход,
  а здесь человек залогинен и просто опечатался.
- `422` — новый пароль короче 8 символов.

## Профиль

Статус: **согласовано**. Нужно к 12 октября (онбординг).

### `GET /users/me`

Текущий пользователь.

Ответ `200`: объект User.

### `PATCH /users/me`

Изменить профиль. Сюда пишет онбординг (город, стиль, цвета) и экран настроек.
Все поля необязательные — передаём только то, что меняем.

Тело запроса:

```json
{
  "name": "Ника",
  "city": "Санкт-Петербург",
  "preferences": {
    "style": "casual",
    "liked_colors": ["black", "gray"],
    "disliked_colors": ["yellow"]
  },
  "avatar_photo_id": 20
}
```

`name` — до 50 символов; `null` или пустая строка стирают имя.

`avatar_photo_id` — фото профиля, `id` из ответа `POST /photos` (тот же
маршрут, что у фото вещи: загрузили файл, получили `id`, привязали).
`null` убирает фото. Одно фото нельзя привязать и к профилю, и к вещи.

**Город** можно задать тремя способами — они соответствуют трём путям в интерфейсе:

| Что прислали | Откуда в интерфейсе | Что делает бэк |
|---|---|---|
| `city` | Человек ввёл название и нажал «Готово» | Ищет город геокодером Open-Meteo, берёт первый результат, сохраняет название и координаты |
| `lat` + `lon` | «Определить автоматически» (геолокация браузера) | Находит название города по координатам через Nominatim (OpenStreetMap), сохраняет его и координаты |
| `city` + `lat` + `lon` | Человек выбрал город из подсказок `GET /geo/cities` | Сохраняет как есть, геокодер не зовёт |

Другие сочетания (`lat` без `lon`, `lon` без `lat`) — `422`. Координаты бэк
округляет до двух знаков перед сохранением.

Третий способ доверяет названию от фронта. Это нормально: человек меняет
только свой профиль, и подсказку он получил от нашего же бэка.

Если человек не дал доступ к геолокации, фронт просто показывает ручной ввод —
запроса к бэку в этом случае нет.

`preferences` заменяется целиком: если прислать только `style`, списки цветов
станут пустыми. Так проще, чем описывать частичное слияние вложенного объекта.

Ответ `200`: обновлённый объект User.

Ошибки:

- `400` — город не найден. По названию — `detail`: «Город не найден, проверь
  название». По координатам (например, точка в море) — «Не удалось определить
  город, введи его вручную».
- `404` — `avatar_photo_id` не существует, фото загружал другой пользователь
  или оно уже привязано к вещи.
- `422` — значение `style` или цвета не из справочника; цвет одновременно в
  `liked_colors` и `disliked_colors`; `lat`/`lon` вне диапазона или переданы
  не парой; имя длиннее 50 символов.
- `502` — Nominatim не ответил. `detail`: «Не удалось определить город, введи
  его вручную». Фронт по этому коду показывает ручной ввод.

## Города

Статус: **согласовано**. Нужно к 12 октября (экран города в онбординге).

### `GET /geo/cities`

Подсказки городов по началу названия — для выпадающего списка на экране города.
Бэк проксирует геокодер Open-Meteo, фронт к нему напрямую не ходит.

Query-параметры:

| Имя | Тип | Обязателен | Описание |
|---|---|---|---|
| q | string | да | Начало названия, от 2 символов |

Ответ `200`:

```json
{
  "cities": [
    { "name": "Москва", "region": "Москва", "country": "Россия", "lat": 55.75, "lon": 37.62 },
    { "name": "Московский", "region": "Москва", "country": "Россия", "lat": 55.6, "lon": 37.35 }
  ]
}
```

- Не больше 5 городов, в порядке, который вернул геокодер.
- Города с одинаковыми `name`, `region` и `country` бэк схлопывает в один
  (остаётся первый): геокодер бывает отдаёт три «Казани» в одной области, и
  человек их не различит. Поэтому городов в ответе может быть меньше 5.
- `region` и `country` бывают `null`: геокодер знает их не для каждого места.
  Тогда фронт показывает только то, что есть.
- `lat`, `lon` округлены до двух знаков, как в профиле. Фронт отправляет их в
  `PATCH /users/me` вместе с `city` без изменений.
- Ничего не нашлось — `cities: []`, это не ошибка.
- Фронт запрашивает с 3 символов и с задержкой ~300 мс после последнего нажатия,
  а не на каждую букву: на 1–2 символа Open-Meteo ищет только точные совпадения.

Ошибки: `422` — `q` короче 2 символов, `502` — Open-Meteo не ответил.

## Гардероб

Статус: **согласовано**. Нужно к 26 октября.

### `GET /items`

Вещи текущего пользователя. Фильтры необязательные, комбинируются через «и».

С 2026-09-30 фильтров в интерфейсе нет: на их месте множественный выбор для
удаления. Параметры оставлены, они дешёвые и пригодятся движку и отладке.
Поиск по названию фронт делает у себя: список целиком уже загружен.

Query-параметры:

| Имя | Тип | Обязателен | Описание |
|---|---|---|---|
| category | string | нет | Значение из справочника `category` |
| color | string | нет | Значение из справочника `color` |
| season | string | нет | Значение из справочника `season`; вещь подходит, если этот сезон есть в её списке |

Ответ `200`:

```json
{
  "items": [ { "...": "объект Item" } ],
  "total": 12
}
```

Сортировка — новые сверху. Пустой гардероб — `items: []`, `total: 0`, это не ошибка.

### `POST /items`

Добавить вещь.

Тело запроса:

```json
{
  "name": "Серый свитер",
  "category": "top",
  "color": "gray",
  "warmth": 3,
  "style": "casual",
  "season": ["demi", "winter"],
  "water_resistance": false,
  "photo_id": 17
}
```

Обязательные: `name`, `category`, `color`, `warmth`. Остальные можно не передавать
(см. Item — что значит их отсутствие).
`photo_id` — из ответа `POST /photos`; можно не передавать, вещь будет без фото.

Ответ `201`: объект Item.

Ошибки:

- `404` — `photo_id` не существует, фото загружал другой пользователь или
  оно уже привязано к другой вещи или к профилю (специально не различаем).
  Одно фото — одна вещь: иначе удаление вещи унесло бы фото у второй вещи или
  у профиля.
- `422` — нет обязательного поля или значение не из справочника.

### `GET /items/{id}`

Одна вещь.

Ответ `200`: объект Item.

Ошибки: `404` — нет такой вещи, `403` — вещь чужая.

### `PATCH /items/{id}`

Изменить вещь. Тело — как у `POST /items`, но все поля необязательные:
передаём только то, что меняем. `"photo_id": null` отвязывает фото.

Ответ `200`: обновлённый объект Item.

Ошибки: как у `POST /items` плюс `403`/`404`.

### `DELETE /items/{id}`

Удалить вещь вместе с фото.

Ответ `204`, без тела.

Ошибки: `403`, `404`.

Вещь пропадает из всех комплектов, где была, включая сегодняшний. Сами
комплекты остаются: дата, погода, объяснение, оценка и отметка «надет» — в
истории не пропадает ни один день. Объяснение не переписывается и может
упоминать вещь, которой в комплекте уже нет. Если вещь была в сегодняшнем
комплекте, новый вариант сам не собирается: «Другой вариант» работает как
обычно, в пределах лимита. *(решено 2026-10-07)*

### `POST /items/bulk-delete`

Удалить несколько вещей сразу — множественный выбор в гардеробе (3.0).
`POST`, а не `DELETE` с телом: тело у `DELETE` часть клиентов и прокси
выбрасывают.

Тело запроса:

```json
{ "ids": [3, 7, 12] }
```

Всё или ничего: если хотя бы одного `id` нет или вещь чужая, не удаляется
ни одна. С комплектами — как у `DELETE /items/{id}`.

Ответ `204`, без тела.

Ошибки:

- `404` — среди `ids` есть несуществующая или чужая вещь. `detail`: «Вещь не
  найдена».
- `422` — `ids` пустой или больше 100 элементов.

## Рекомендации

Статус: **согласовано**. Нужно к 9 ноября. Главный раздел документа.

Как это работает: бэк берёт город из профиля, тянет прогноз Open-Meteo на
сегодня (с кешем на час, чтобы не ходить к ним на каждое обновление
страницы), отдаёт погоду и гардероб движку Насти, получает комплект и
объяснение, сохраняет комплект в базу и отдаёт фронту.

Комплект на день считается один раз и потом отдаётся тот же самый —
иначе при каждом обновлении страницы человек видел бы новый набор, а
оценивать было бы нечего. Новый вариант — только явным запросом.

Варианты: за день можно получить не больше `variants_max` комплектов (по
умолчанию 3 — исходный и два «других варианта»). Лимит нужен, потому что
комбинаций в гардеробе конечное число, и после третьего варианта движок
начинает предлагать почти то же самое. Все варианты дня хранятся, между ними
можно переключаться, один из них выбран — это и есть комплект дня. В историю
попадает выбранный.

Как движок трактует невыбранные варианты — как слабое «не нравится» или
никак, — решает Настя на этапе 4. API только хранит, какой вариант выбран.

Все три эндпоинта ниже отвечают одним и тем же объектом OutfitDay, так что
фронт после любого действия просто перерисовывает экран из ответа.

### `GET /outfit/today`

Комплект на сегодня со всеми вариантами. Если на сегодня ещё ничего нет —
соберёт первый вариант.

Ответ `200`: объект OutfitDay.

Если подходящих вещей не хватило, это всё равно `200`: в `items` — то, что
нашлось, в `missing` — чего не хватило, в `explanation` — человеческое
объяснение («В гардеробе нет верхней одежды под дождь»). Пустой гардероб —
тоже `200`, `items: []`, объяснение про пустой гардероб. Фронт рисует один
и тот же экран во всех случаях и не делает особых веток по кодам.

Ошибки:

- `400` — в профиле не указан город. `detail`: «Укажи город в профиле». Фронт
  по этому коду отправляет на экран города.
- `502` — Open-Meteo не ответил. `detail`: «Не удалось получить прогноз, попробуй позже».

### `POST /outfit/today/regenerate`

Кнопка «Другой вариант». Собирает новый вариант на сегодня на той же погоде,
добавляет его в конец и делает выбранным. Прошлые варианты остаются, к ним
можно вернуться. Тела нет.

Ответ `201`: объект OutfitDay с новым вариантом.

Ошибки:

- `400`, `502` — как у `GET /outfit/today`.
- `409` — движок не нашёл ничего, что отличалось бы от уже показанных
  вариантов. Новый вариант не создаётся и лимит не тратится.
  `detail`: «Другого варианта под эту погоду в гардеробе нет».
- `409` — сегодняшний комплект уже отмечен как надетый.
  `detail`: «Комплект на сегодня уже отмечен как надетый. Сними отметку, чтобы выбрать другой».
- `429` — лимит вариантов на сегодня исчерпан.
  `detail`: «На сегодня вариантов больше нет».

### `POST /outfit/{id}/select`

Сделать выбранным другой вариант сегодняшнего дня — возврат к прошлому
варианту. Фронт вызывает его при каждом переключении: какой вариант на экране,
тот и выбран. Тела нет.

Ответ `200`: объект OutfitDay.

Ошибки:

- `400` — вариант не сегодняшний. `detail`: «Выбрать можно только сегодняшний вариант».
- `403`, `404` — чужой комплект или такого нет.
- `409` — сегодняшний комплект уже отмечен как надетый (текст как у `regenerate`).

## Оценки и история

Статус: **черновик**. Этап 4, к 23 ноября. Уточним, когда движок начнёт
учитывать оценки, — формат зависит от того, что Насте нужно на входе.

### `POST /outfit/{id}/feedback`

Оценить комплект и/или отметить, что его надели.

Тело запроса:

```json
{
  "rating": "like",
  "worn": true
}
```

- `rating` — `like` или `dislike`, необязательно. Можно поставить любому
  варианту дня.
- `worn` — надел ли комплект, необязательно. Нужно для истории носки: то, что
  надевали вчера, движок сегодня не предлагает. `true` можно поставить только
  выбранному варианту. Пока стоит `worn: true`, переключать и перегенерировать
  варианты этого дня нельзя: что надето, то надето. `worn: false` снимает отметку.

Ответ `200`: объект Outfit с заполненным `feedback`:

```json
"feedback": { "rating": "like", "worn": true, "created_at": "2026-11-09T09:00:00Z" }
```

Повторный запрос перезаписывает оценку. Ошибки: `400` — `worn: true` для
невыбранного варианта (`detail`: «Отметить можно только выбранный вариант»),
`403`, `404`, `422`.

### `GET /outfit/history`

Прошлые комплекты с оценками, новые сверху. По одному на день — выбранный
вариант, невыбранные в историю не попадают.

Query: `from`, `to` — даты `YYYY-MM-DD`, необязательные. По умолчанию — последние 30 дней.

Ответ `200`:

```json
{
  "outfits": [ { "...": "объект Outfit" } ],
  "total": 14
}
```

## Распознавание фото

Статус: **согласовано** (2026-10-07). Делаем сразу, не дожидаясь этапа 4.

### `POST /items/recognize`

Определить категорию и цвет по загруженному фото. **Только предзаполняет
форму** — вещь в базу не пишет, это делает человек через `POST /items`.

Тело запроса:

```json
{ "photo_id": 17 }
```

Ответ `200`:

```json
{
  "category": { "value": "top", "confidence": 0.81 },
  "color": { "value": "gray", "confidence": 0.93 }
}
```

- `confidence` — от 0 до 1. Ниже порога — поле не предзаполняем, `value: null`,
  пользователь выбирает сам; `confidence` при этом всё равно приходит. Порог —
  настройка бэка `RECOGNITION_THRESHOLD`, по умолчанию 0.5. Поменяем по итогам
  эксперимента Насти, фронт его не хардкодит.
- Категория — по CLIP: какое из описаний категорий больше похоже на фото.
  Цвет — по rembg + k-means: убираем фон, берём основной цвет вещи и ищем
  ближайший из справочника. Нет одного основного цвета — `multicolor`.
- Медленный запрос: CLIP на процессоре — секунды. Фронту показать спиннер, а не
  считать, что зависло. Модели лежат в образе бэка, интернет для распознавания
  не нужен.

Ошибки: `404` — нет такого фото или оно чужое (не различаем, как у
`POST /items`), `422` — нет `photo_id`.
