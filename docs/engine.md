# Движок подбора: как его вызывает бэк

Ответственные: Настя (что внутри движка) и Ника (как бэк его вызывает).
Статус: **согласовано** (2026-10-07, Настя: «делать как считаешь нужным»).

Здесь только граница между бэком и движком: что движок получает и что
отдаёт. Как он внутри выбирает вещи, решает Настя, и сюда это не пишем.
Форматы ответов фронту — в `API.md`, раздел «Рекомендации».

## Главное правило: движок — обычная функция

Движок не ходит в базу, в сеть и в файлы. Всё, что ему нужно, бэк передаёт
на вход, а результат бэк сам сохраняет и отдаёт фронту.

Зачем так:

- Настя пишет и проверяет движок без Docker и базы: собрала вход руками,
  вызвала функцию, посмотрела ответ. Так же устроен эксперимент.
- Права, транзакции, лимит вариантов и коды ошибок остаются на бэке, движку
  про них знать не нужно.
- Бэк можно доделать раньше движка: пока движка нет, на его месте временная
  заглушка с той же сигнатурой (см. ниже).

Код движка лежит в `backend/app/engine/`. Бэк импортирует оттуда только то,
что описано в этом файле: `build_outfit`, классы входа и выхода и
`NoNewVariant`. Остальное внутри папки Настя устраивает как хочет.

## Вызов

```python
from app.engine import build_outfit

result = build_outfit(request)  # OutfitRequest -> OutfitResult
```

Вызов синхронный. На гардеробе в несколько десятков вещей он должен
укладываться в доли секунды: его ждёт человек на главном экране.

## Вход: `OutfitRequest`

```python
from dataclasses import dataclass, field
from datetime import date


@dataclass(frozen=True)
class WeatherInput:
    temp_min: float            # °C
    temp_max: float            # °C
    feels_like: float          # °C, минимум «ощущается как» за светлое время
    wind_speed: float          # м/с, дневной максимум
    precipitation: float       # мм за день
    precipitation_probability: int | None  # %, None — Open-Meteo не отдал
    condition: str             # clear | cloudy | rain | snow


@dataclass(frozen=True)
class ItemInput:
    id: int
    name: str
    category: str              # значения — из attributes.md
    color: str
    warmth: int                # 1–5
    style: str | None          # None — подходит под любой стиль
    seasons: frozenset[str]    # пусто — всесезонная
    water_resistance: bool


@dataclass(frozen=True)
class Preferences:
    style: str | None          # None — не выбран, подходят все стили
    liked_colors: frozenset[str]
    disliked_colors: frozenset[str]


@dataclass(frozen=True)
class OutfitRequest:
    date: date                       # «сегодня» в часовом поясе города пользователя
    weather: WeatherInput
    wardrobe: list[ItemInput]        # все вещи пользователя, чужих тут нет
    preferences: Preferences
    worn_yesterday: frozenset[int] = frozenset()      # id вещей из комплекта, отмеченного «надет» вчера
    shown_today: list[frozenset[int]] = field(default_factory=list)  # вещи уже показанных вариантов дня
```

- **`date`** движок может использовать, чтобы понять сезон. Брать ли сезон по
  месяцу или по температуре, решает Настя.
- **`worn_yesterday`** нужен для правила «вчера надевали — сегодня не
  предлагаем». Бэк собирает его из истории носки (см. `db-schema.md`, «История
  носки»). Как строго соблюдать правило, если без этих вещей комплект не
  собирается, решает Настя.
- **`shown_today`** пустой при первом комплекте дня. При «Другом варианте» в нём
  наборы вещей всех уже показанных вариантов: новый вариант не должен
  совпасть ни с одним из них.
- **Оценки** (`like` / `dislike`) на вход пока не идут. Их добавим отдельным
  полем, когда согласуем раздел «Оценки и история» в `API.md` на этапе 4.

## Выход: `OutfitResult`

```python
@dataclass(frozen=True)
class OutfitResult:
    item_ids: list[int]   # вещи комплекта, только из request.wardrobe
    explanation: str      # текст для человека, не пустой
    missing: list[str]    # категории, которых не хватило, значения из attributes.md


class NoNewVariant(Exception):
    """Нет комплекта, который отличался бы от всех в shown_today."""
```

- **`item_ids`** — по одной вещи на категорию, как в `attributes.md`: верх (или
  платье), низ, при необходимости верхняя одежда и обувь. Может быть пустым:
  пустой гардероб — не ошибка.
- **`explanation`** показывается человеку как есть, по-русски, на «ты», как и
  остальные тексты интерфейса.
- **`missing`** — категории, без которых комплект на эту погоду неполный
  (например, `["outerwear"]` в дождь без водостойкой верхней одежды). Пустой
  список — всё нашлось.
- **`NoNewVariant`** движок бросает, только если `shown_today` не пустой и
  ничего нового собрать нельзя. Бэк отвечает на это `409` и лимит не тратит
  (`API.md`, `POST /outfit/today/regenerate`).

Любое другое исключение из движка — ошибка в коде. Бэк отвечает `500` и
пишет его в лог.

## Что делает бэк вокруг вызова

- Берёт погоду на сегодня (кеш на час, `weather_records`) и по ней определяет
  `date`. Нет города — `400`, Open-Meteo не ответил — `502`. До движка дело
  не доходит.
- Собирает вход из базы: гардероб, предпочтения из профиля, вчерашний надетый
  комплект, уже показанные варианты дня.
- Проверяет, что `item_ids` есть в гардеробе, и сохраняет результат в
  `outfits` и `outfit_items`.
- Следит за лимитом вариантов (`429`), отметкой «надет» (`409`) и выбранным
  вариантом.

## Временная заглушка

Пока движка нет, в `backend/app/engine/` лежит простая заглушка с той же
сигнатурой: по одной подходящей по теплоте вещи на категорию и объяснение
«Это временный подбор, настоящий движок ещё в работе». Она нужна, чтобы
эндпоинты рекомендаций и главный экран на фронте делались параллельно с
движком. Настя заменяет её своим кодом, сигнатуру не трогая.
