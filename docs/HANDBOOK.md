# Как мы работаем над Layers

Общая инструкция команды: кто за что отвечает, какие сроки, как пользоваться
гитом, как проходит ревью и какие решения уже приняты. Если сомневаешься, как
что-то сделать, сначала загляни сюда. Не нашла ответа — спроси в чате, а потом
допиши ответ в этот файл, чтобы следующей не пришлось спрашивать.

Как поднять проект локально, описано в [README](../README.md). Здесь этого нет.

## 1. Как обновлять этот документ

- Этот файл правим так же, как код: отдельная ветка `docs/...`, pull request,
  ревью Ники. Напрямую в `main` не пушим.
- Приняли решение в чате или на созвоне — в течение дня добавь его в раздел 8
  с датой. Решение, которое есть только в переписке, через неделю никто не
  найдёт.
- Решение поменялось — старую строку не удаляй, а зачеркни (`~~текст~~`) и
  допиши рядом новую с датой. Так видно, почему было по-другому.
- Вопрос закрыт — перенеси его из раздела 9 в раздел 8.
- Детали контракта (поля, коды ответов, значения атрибутов) сюда не
  копируем: они живут в `API.md`, `attributes.md` и `db-schema.md`. Здесь
  только само решение, коротко, и ссылка на файл с подробностями.
- Сроки продублированы в `README.md`. Если меняешь дату, поправь в обоих
  местах в одном PR.

Код заканчиваем **21 декабря**, защита в начале января. Проект принимает один
преподаватель, комиссии не будет.

| **9 ноября** | **Первая рекомендация по погоде на экране** |
| 23 ноября | Оценки, история носки, распознавание фото |
| 7 декабря | Партнёрские товары, эксперимент по точности |
| 14 декабря | Тексты разделов отчёта переданы Насте |
| 21 декабря | Всё собрано, протестировано, отчёт написан |
| 5 января | Презентация и прогон защиты |

### Главное правило приоритетов

Ключевая точка — **9 ноября**. Если к этой дате рекомендации на экране нет,
режем распознавание фото и партнёрские товары. Защититься можно с ручным
вводом вещей и работающим подбором, но не наоборот.

Отсюда порядок: сначала то, что нужно к ближайшей контрольной точке, потом
то, что держит чужую работу (см. «Кто кого держит»), и только потом всё
остальное. Хочешь взяться за что-то из дальнего этапа — сначала проверь, не
горит ли ближний.

### Что считается «готово»

Фича готова, когда она **смержена в `main` через PR и запускается в
`docker compose up`**. Код у тебя на компьютере или в неоткрытой ветке в
прогресс не засчитывается, ни в отчёте координатору, ни внутри команды.

## 4. Источники правды

У каждого вида информации ровно один файл, где она правильная. Если в двух
местах написано по-разному, прав файл из этой таблицы, а второе место надо
поправить.

| Что | Где | Кто отвечает |
|---|---|---|
| Эндпоинты, форматы запросов и ответов, коды ошибок | `docs/API.md` | Ника |
| Названия атрибутов одежды и их значения | `docs/attributes.md` | Настя |
| Таблицы и поля базы | `docs/db-schema.md` | Настя |
| Какие данные нужны каждому экрану | `docs/frontend-screens.md` (пока в ветке `docs/frontend-screens`) | Саша |
| Макеты | Figma: https://www.figma.com/design/6STtRl8uzfEyVRKILRomJj | Саша |
| Как работаем и что решили | этот файл | все, ревью Ники |
| Запуск и структура репо | `README.md` | Ника |

### Сначала документ, потом код

1. Нужен новый эндпоинт или поле? Сначала PR с правкой `API.md`.
2. Обсуждаем и согласуем в PR.
3. Мержим, и только после этого пишем код.

Если в `API.md` нужного нет, формат не придумываем «пока так», а описываем и
согласовываем. У разделов `API.md` есть статус: по **согласованным** пишем
код, по **черновикам** нет.

### Поменять название атрибута

Порядок всегда один: `attributes.md` → `db-schema.md` → `API.md` → код бэка
и фронта. Лучше одним PR, чтобы ничего не разъехалось. Машинные значения
(`top`, `casual`) меняем только в крайнем случае, подписи для интерфейса
можно спокойно.

## 5. Работа с гитом по шагам

`main` защищён: напрямую в него запушить нельзя, только через pull request.
Команды ниже одинаковые для macOS (Терминал) и Windows (Git Bash или
PowerShell).

### Один раз: скачать репозиторий

```bash
git clone https://github.com/zeawale/layers.git
cd layers
```

Появится папка `layers` со всем проектом. Дальше все команды выполняй внутри
неё: если терминал пишет `not a git repository`, значит, ты не в той папке.

### Начать задачу

```bash
git switch main
git pull
git switch -c feat/wardrobe-list
```

Что происходит: переходим на `main`, подтягиваем свежую версию с GitHub и от
неё создаём свою ветку. Ветку всегда создаём от **свежего** `main`, иначе
потом будут лишние конфликты.

Как называть ветку: `тип/что-делаем`, латиницей, слова через дефис.

| Префикс | Когда | Пример |
|---|---|---|
| `feat/` | Новая функциональность | `feat/login-page`, `feat/outfit-engine` |
| `fix/` | Исправление ошибки | `fix/login-error` |
| `docs/` | Только документы | `docs/api-design-sync` |
| `chore/` | Настройки, зависимости, докер | `chore/update-deps` |

Одна ветка — одна задача. Не надо делать в одной ветке и вход, и гардероб:
такой PR тяжело проверять и страшно мержить.

### Сохранить работу (коммит)

```bash
git status                  # что изменилось
git add путь/к/файлу        # добавить конкретный файл
git commit -m "Гардероб: список вещей с фильтром по категории"
```

`git add .` добавляет всё подряд. Перед этим посмотри `git status`: туда не
должны попасть `.env`, `node_modules`, `.venv` и личные файлы.

Сообщение коммита — по-русски, в формате «Область: что сделано». Так уже
написаны все коммиты в репо:

- `Авторизация: регистрация и вход по email`
- `Схема базы: свести с API.md`
- `Онбординг: шаг выбора города`

Плохие примеры: `fix`, `правки`, `asdf`, `update App.jsx`. Через месяц по ним
не понять, что изменилось.

В сообщениях коммитов **не должно быть** строк `Co-Authored-By` и ссылок на
сессии ИИ-помощников. Если помощник их подставил, убери перед коммитом.

Коммить часто, маленькими шагами: сделала кусок, который работает, —
закоммитила.

### Отправить на GitHub

```bash
git push -u origin feat/wardrobe-list
```

`-u` нужен только при первом пуше ветки. Дальше хватит `git push`.

### Подтянуть свежий main в свою ветку

Если пока ты работала, в `main` что-то смержили, и особенно если GitHub пишет
в PR «This branch has conflicts»:

```bash
git pull --rebase origin main
```

Git переставит твои коммиты поверх свежего `main`. Если будут конфликты, см.
раздел 11. После rebase обычный `git push` откажет. Пушь так:

```bash
git push --force-with-lease
```

`--force-with-lease` безопаснее, чем `--force`: он не затрёт чужие коммиты,
если кто-то успел запушить в твою ветку. Делаем это **только в своей ветке**,
никогда в `main`.

### После того как PR смержили

```bash
git switch main
git pull
git branch -d feat/wardrobe-list
```

Удаляем локальную ветку: она больше не нужна, вся работа уже в `main`.

## 6. Pull request и ревью

### Открыть PR

После `git push` GitHub покажет кнопку **Compare & pull request** (или
открой ссылку из вывода `git push`).

- **Base:** `main`.
- **Заголовок:** как у коммита, «Область: что сделано».
- **Описание** по шаблону:

```markdown
Что сделано:
- ...

Как проверить:
1. docker compose up
2. Открыть http://localhost:5173/...
3. Должно получиться ...

На что посмотреть ревьюеру:
- то, в чём не уверена

Связано с: этап / задача
```

«Как проверить» — самая важная часть. Без неё ревью превращается в
угадайку.

### Как проходит ревью

- Все PR ревьюит Ника. Сама свой PR не мержим.
- Замечания бывают двух видов:
  - **«надо поправить»** — без этого не мержим. Сначала то, что ломается:
    доступ к чужим данным, нет проверки прав, необработанные ошибки, секреты
    в коде, запросы к базе в цикле.
  - **«на будущее»** — можно оставить как есть, это на следующий раз. За
    одно ревью их не больше пяти.
- Если код работает, но написан странно, а дедлайн близко, ревьюер так и
  пишет: «работает, переписывать сейчас не стоит».
- Поправила замечание — отвечай в треде («поправила в коммите такой-то») и
  пушь в ту же ветку. Новый PR открывать не надо, он обновится сам.
- Не согласна с замечанием — пиши в треде, почему. Это нормально, ревью —
  разговор, а не экзамен.
- Мержим кнопкой **Merge pull request** после одобрения. Потом удаляем ветку
  на GitHub (кнопка появится сразу после мержа).

### Чего от PR ждём

- Проект поднимается через `docker compose up`, ничего не падает.
- В PR нет `.env`, паролей, токенов и ключей.
- Если менялся контракт, `API.md` уже обновлён и смержен раньше кода.
- Новая переменная окружения добавлена в `.env.example` с заглушкой.

## 7. Правила для кода

### Для всех

- **Секреты только в `.env`.** Он в `.gitignore` и в репозиторий не
  попадает. В коде и примерах — переменные окружения, не значения. Добавила
  новую переменную — добавь её в `.env.example` с заглушкой, иначе у
  остальных ничего не заведётся.
- **Атрибуты одежды не хардкодим.** Все списки (категории, цвета, стили,
  сезоны) берутся из справочника: на фронте через `GET /attributes`, на
  бэке из одного места в коде.
- **Распознавание фото только предзаполняет форму.** В базу вещь сохраняет
  человек, нажав «Сохранить». Решения, где модель пишет в базу сама, не
  принимаем.
- **Интерфейс только под мобильный экран** шириной 390 px. Десктоп не делаем.

### Бэкенд

- Каждый объект с владельцем отдаём только владельцу. Чужой объект — `403`,
  несуществующий — `404`. Проверка прав есть в **каждом** эндпоинте, который
  принимает `id`.
- Текст ошибки — `{"detail": "..."}` по-русски, так, чтобы его можно было
  показать пользователю как есть.
- Допустимые значения атрибутов проверяет Pydantic. В базе они хранятся как
  `text`.
- Запросы к базе не делаем в цикле: если нужно достать вещи для десяти
  комплектов, это один запрос, а не десять.

### Фронтенд

- Адрес бэкенда знает только `frontend/src/api/`. В компонентах
  `http://localhost:8000` не пишем.
- Токен лежит в `localStorage`. На любой `401` фронт чистит токен и
  отправляет на экран входа.
- Текст ошибки с бэка (`detail`) можно показывать как есть. Исключение —
  `422`: там `detail` — список ошибок по полям, его надо разобрать.

### База

- Таблицы — множественное число, нижний регистр: `users`, `items`.
- Поля — `snake_case`. Внешние ключи — `user_id`, `item_id`.
- У каждой пользовательской сущности есть `user_id`.
- Полные правила — в начале `docs/db-schema.md`.

## 8. Принятые решения

Здесь то, о чём уже договорились. Коротко: что решили и почему. Подробности
в файле, указанном в скобках.

### Архитектура и стек

- **Монорепо:** `backend/`, `frontend/`, `docs/` в одном репозитории. Одна
  правка контракта — один PR, бэк и фронт не разъезжаются. *(README)*
- Стек: PostgreSQL 16, Python 3.12 + FastAPI + SQLAlchemy 2, React 18 + Vite
  + MUI + react-router, Open-Meteo для погоды, CLIP + rembg + k-means для
  распознавания, Docker Compose для запуска. *(README)*
- Все значения, которые могут поменяться (лимит вариантов, адрес фронта для
  писем), живут в настройках бэка, а не в коде.
- **Таблицы создаются миграциями Alembic** (2026-10-01). Бэкенд при старте
  в Docker Compose сам выполняет `alembic upgrade head`. Поменяла модель —
  добавь миграцию в том же PR. `create_all` не используем: он не умеет
  менять уже созданные таблицы, и после каждой правки схемы всем пришлось бы
  сносить базу. *(README)*

### Авторизация и профиль

- Один JWT-токен на 7 дней, без refresh-токена. Протух — `401`, человек
  входит заново. Так проще, а для учебного проекта хватает. *(API.md)*
- Регистрация сразу возвращает токен, отдельно логиниться не нужно.
- Ошибка входа одинаковая для «нет такого email» и «неверный пароль»: по
  ответу нельзя узнать, кто зарегистрирован.
- **Имя** (`name`) необязательное, до 50 символов. Нет имени — пишем
  приветствие без него. *(API.md)*
- **Сброс пароля** по ссылке из письма. Ответ на запрос ссылки всегда один и
  тот же, есть email или нет. Токен одноразовый, живёт 60 минут, в базе
  хранится только его хеш. После сброса все старые токены входа перестают
  работать, а человек сразу залогинен. Код — после 9 ноября. *(API.md)*
- **Город** задаётся тремя способами: ввести название, «Определить
  автоматически» (геолокация браузера + Nominatim) или выбрать из подсказок
  `GET /geo/cities`. Координаты храним с точностью до двух знаков (~1 км):
  для прогноза хватает, точный адрес нам не нужен. *(API.md)*
- **Подсказки городов оставляем** (2026-10-01). Без них ввод названия
  промахивается: по запросу «питер» геокодер находит деревню Питер в Пермском
  крае, а не Санкт-Петербург. Человек видит регион и выбирает нужный город
  сам. *(API.md)*
- **Онбординг считается пройденным, когда указан город.** Стиль и цвета
  можно пропустить: без стиля движок подбирает вещи любого стиля. Шаг города
  пропустить нельзя, без него нет погоды. *(API.md)*
- Один цвет не может быть одновременно в «Люблю носить» и «Не ношу». *(API.md)*
- `preferences` в `PATCH /users/me` заменяется целиком, без частичного
  слияния.
- **Смена пароля из профиля** (2026-09-30): `POST /auth/password/change` со
  старым и новым паролем. Неверный старый пароль — `400`, не `401`, чтобы
  фронт не выкинул человека на вход. Старые токены перестают работать, в
  ответе новый. *(API.md)*
- **Фото профиля** (2026-09-30): поле `avatar` у пользователя, грузится
  через тот же `POST /photos`, что и фото вещи. Нет фото — показываем первую
  букву имени. *(API.md)*

### Справочник атрибутов

- **Категории:** Верх, Низ, Платье, Верхняя одежда, Обувь, Аксессуары. В
  комплекте по одной вещи на категорию. Платье закрывает верх и низ сразу.
  Подслоёв (футболка под свитер) нет: тёплый и лёгкий верх различаются
  теплотой. *(attributes.md)*
- **Цвета:** 16 крупных групп, среди них «Разноцветная» (`multicolor`).
  Группы крупные, потому что цвет определяется по фото, а из кластера
  пикселей точный оттенок не вытащить. *(attributes.md)*
- **Теплота:** число 1–5, обязательна. Без неё движок не видит вещь.
- **Стили:** три, Спортивный, Повседневный, Деловой (`sport`, `casual`,
  `business`). Хочешь больше — сначала справочник, потом макет. *(attributes.md)*
- **Сезоны:** Лето, Демисезон, Зима, можно несколько. Не выбран ни один —
  вещь всесезонная. Весны и осени по отдельности нет.
- Обязательные поля вещи: название, категория, цвет, теплота. Стиль, сезон и
  защита от осадков необязательны. Материала нет: распознавание его не
  определяет, а движку он не нужен.

### Гардероб и фото

- Фото живёт отдельно от вещи: сначала `POST /photos`, потом `POST /items` с
  `photo_id`. Один файл идёт и на распознавание, и на вещь. *(API.md)*
- Принимаем JPEG, PNG, WebP до 10 МБ. Бэк сжимает до 1024 px и хранит как
  JPEG. HEIC не принимаем. Фото без вещи удаляется через сутки.
- Пагинации нет: у одного человека десятки вещей, не тысячи.
- **Фильтров в гардеробе нет** (2026-09-30): вместо них множественный выбор
  и удаление сразу нескольких вещей через `POST /items/bulk-delete`. Всё или
  ничего: одна чужая или несуществующая вещь — не удаляется ни одна.
  Параметры фильтров в `GET /items` оставлены, фронт их не использует. *(API.md)*
- Распознавание определяет только категорию и цвет. При низкой уверенности
  поле не предзаполняется.
- **Удалённая вещь пропадает из комплектов** (2026-10-07): сами комплекты,
  оценки и отметки «надет» остаются, история не теряет дни. Не мягкое
  удаление — иначе в каждом запросе к гардеробу нужен фильтр «не удалена», и
  стоит его забыть, движок предложит удалённую вещь. *(API.md, db-schema.md)*

### Погода и рекомендации

- Прогноз из Open-Meteo, кеш на час. «Ощущается как» — минимальная за
  светлое время суток: одеваемся под худший момент дня. *(API.md)*
- Состояние погоды — ровно четыре: ясно, облачно, дождь, снег.
- Вероятность осадков (%) показываем на фронте, движок смотрит на осадки в
  мм. *(API.md)*
- Комплект на день собирается **один раз** и потом отдаётся тот же. Иначе
  при каждом обновлении страницы был бы новый набор и оценивать было бы
  нечего.
- **Варианты:** не больше 3 в день. Все варианты хранятся, между ними можно
  переключаться. Выбранный вариант — это комплект дня, он и попадает в
  историю. Лимит, потому что после третьего варианта движок начинает
  повторяться. *(API.md)*
- Отметили «Надел» — переключать и перегенерировать варианты этого дня
  нельзя: что надето, то надето. Сначала сними отметку. *(API.md)*
- Нет другого варианта — ошибка `409`, лимит не тратится. *(API.md)*
- В комплекте столько вещей, сколько собрал движок (летом без куртки, с
  платьем без низа). Интерфейс рисует столько карточек, сколько пришло, а не
  пять фиксированных ячеек.
- Если вещей не хватило, это не ошибка: в ответе будет `missing` и
  объяснение словами.

### Дизайн

- Только мобильная версия, 390 px.
- Подписи на карточках вещей — названия категорий из справочника («Верх»,
  «Низ»…), а не «Основа» и «Верхний слой».
- Партнёрские товары показываются на месте недостающей вещи (в пустом
  слоте), а не в отдельной шторке.
- **Идеи на будущее** (в макетах есть, в коде не делаем, на защите покажем
  как план развития): цветотип по селфи, замена одной вещи в комплекте,
  «идея дня», уведомления, выбор языка, «где чаще одеваетесь», статистика
  носки по вещи, календарь истории.
- **Выкинули совсем:** виртуальную примерку. Её нет ни в плане, ни в стеке.

## 10. Отчётность

### Координатору

- Раз в неделю, **по четвергам**, одним сообщением в общем чате. Пишет Ника
  от лица команды.
- Формат: в начале «X/100%» выполненного, дальше ход работы, проблемы и как
  их решаем.
- Прогресс считаем по этапам из календаря (раздел 3). Этап засчитывается
  только если смержен в `main` и запускается в Docker Compose.
- К концу семестра координатор ждёт 100%, минимум 85–90%.
- Созвоны с координатором тоже по четвергам, в Яндекс Телемосте.

### Внутри команды

- **Каждую среду вечером** Саша и Настя присылают Нике свой кусок отчёта:

  ```
  #номер — название задачи
  Абзац: что сделано, что не получилось, что мешает.
  ```

- Застряла — пиши сразу, не жди среды. Особенно если задача держит кого-то
  ещё (раздел 2).
- **14 декабря** тексты разделов итогового отчёта передаём Насте, она
  собирает отчёт.

## 11. Если что-то сломалось

### `not a git repository`

Ты не в папке проекта. Перейди в неё: `cd путь/к/layers`. На macOS проект
обычно в `~/dev/layers`, на Windows — в `C:\dev\layers`.

### Конфликт при `git pull --rebase`

Git остановится и напишет, в каких файлах конфликт. В этих файлах появятся
куски вида:

```
<<<<<<< HEAD
как в main
=======
как у тебя
>>>>>>> твой коммит
```

1. Открой файл, оставь правильный вариант (или собери из обоих), удали
   строки с `<<<<<<<`, `=======`, `>>>>>>>`.
2. `git add путь/к/файлу`
3. `git rebase --continue`

Запуталась — `git rebase --abort` вернёт всё как было до rebase. Потом
напиши Нике, разберём вместе.

### Случайно закоммитила `.env` или пароль

Не пушь. Напиши Нике сразу. Если уже запушила, пароль или ключ считаем
утёкшим и меняем, даже если потом удалили файл: в истории гита он
остаётся.

### Запушила не в ту ветку или всё сломалось

Ничего не удаляй и не делай `--force` наугад. Напиши в чат, что делала и что
выводит `git status`. В гите почти всё можно вернуть, если не натворить
лишнего.

### Проект не поднимается

См. раздел «Запуск» в `README.md`. Логи бэкенда: `docker compose logs
backend`. После правки `requirements.txt`: `docker compose build backend`.
